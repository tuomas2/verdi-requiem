# 2026-09-10 (f): CI's mupdf is older, and its outline reader is broken

The user reported that CI had gone red after the previous entry
(*2026-09-10 (e)*, the table of contents), with a traceback that pointed
nowhere useful:

    UnicodeDecodeError: 'utf-8' codec can't decode byte 0xbf
    in position 1831: invalid start byte

All 433 tests pass on this machine. The failure is real, it is in
`linkit.py`, and it is a version difference: **CI's `mutool` is mupdf
1.23.10** (ubuntu-24.04's `mupdf-tools`), this machine's is 1.27.0.

## What is actually broken

`linkit.lue` read the bookmarks back with `doc.outlineIterator()`. In 1.23.10
that iterator's JS binding returns garbage:

- `item().title` returns the **wrong** bookmark's name — the same one over and
  over, in the run below always the last one;
- `item().uri` returns a *name* where the URI belongs;
- and uninitialised memory comes along with it, so the JSON is not valid UTF-8
  and `subprocess(text=True)` raises before the caller ever sees a string.

Read with 1.23.10, the same PDF that reads correctly here comes back as

    {"nimi":"VII  Libera me","uri":"II·9  Confutatis"},
    {"nimi":"\xbb\x81\x97?","uri":"II·10  Lacrymosa"}, …

which is why the byte named in the error changed from run to run: 0xbf and
0x8b in the user's two CI logs, 0xb2 and 0xfc in two local runs against the
same binary.

**The parts themselves are fine.** Writing works on 1.23.10 — a PDF built with
it has exactly the right `/Title` entries, UTF-16BE with BOM where the name
contains `·`, ASCII literals elsewhere. Only the verification step was blind,
which is the part that has to be trustworthy: a written link is a claim, and
`lue` is what checks it.

## The fix

`doc.loadOutline()` returns the whole outline as an array of
`{title, uri, down}` and gives **byte-identical output on 1.23.10 and 1.27.0**.
`LUE_JS` uses it now. Our own writer never makes sub-entries, so `down` is not
walked; that is stated in the comment beside it.

Two smaller things went in at the same time, both about not letting the
environment decide an encoding: `aja_js` now writes its JS temp file with
`encoding="utf-8"` (the script contains `·` and `ä ö å é` for the font
metrics, and the file was being written in the locale's encoding), and reads
the output with `encoding="utf-8"` instead of `text=True`.

## The method worth repeating

Nothing about this was diagnosable from the traceback, and guessing at it
wasted the first twenty minutes — the suspects were mutool's text extraction,
the locale in the runner, and the font metrics, and none of them was it. What
settled it in one step was **running the suite against CI's own binary**:

    curl -O http://archive.ubuntu.com/ubuntu/pool/universe/m/mupdf/mupdf-tools_1.23.10+ds1-1build3_amd64.deb
    curl -O http://archive.ubuntu.com/ubuntu/pool/universe/g/gumbo-parser/libgumbo2_0.12.0+dfsg-2build1_amd64.deb
    dpkg-deb -x mupdf-tools_*.deb old && dpkg-deb -x libgumbo2_*.deb old
    # a one-line wrapper on PATH that sets LD_LIBRARY_PATH and execs old/usr/bin/mutool
    PATH=$PWD/bin:$PATH python3 -m unittest discover -s testit -t .

`libgumbo2` is the only dependency the older `mutool` needs that this machine
does not already have (it wants `libgumbo.so.2`, we ship `.so.3`). It does not
have to be installed — unpacking both debs next to each other is enough, and
nothing touches the system's own 1.27.0. That reproduced the failure exactly,
and the fixed suite then passes under **both** versions, which is the check
that the fix is a fix and not a coincidence.

The environment note is in [`docs/ymparisto.md`](../ymparisto.md), beside the
other `mutool run` measurements, because the next person to reach for
`outlineIterator` will read that file and not this one.
